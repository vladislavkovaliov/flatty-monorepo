# Задача 11. Git-гигиена: чистый коммит-лог

> Тема: **conventional commits + интерактивный rebase** — привести историю в вид,
> который не стыдно показать на собеседовании.
> Результат: осмысленные, атомарные коммиты с внятными сообщениями и (опционально)
> автоматической проверкой формата перед коммитом.

---

## Зачем

На техлид-собесе тебя почти гарантированно попросят показать репозиторий и спросят
«как ты ведёшь коммиты». Это самый быстрый способ оценить дисциплину инженера: по
`git log --oneline` опытный ревьюер за 30 секунд понимает, умеешь ли ты разбивать
работу на осмысленные шаги и писать сообщения, по которым можно восстановить
«почему».

Сейчас в истории есть:

- `feat: test` — два одинаковых коммита подряд (ничего не говорит ни о чём);
- `feat: updates workflows` — сообщение в стиле «что-то обновил», без контекста;
- `feat: adds agent loop to real ollama model` — **три одинаковых** коммита подряд
  (явно один и тот же кусок работы коммитился трижды, без squash).

Для позиции архитектора это сигнал «не контролирует границы работы и не рефлексирует
над историей». Починка — это не только косметика: она заставляет выработать привычку
коммитить атомарно, а атомарные коммиты — основа нормального code review и
`git bisect`.

## Контекст проекта

- Репозиторий — один `main` (портфолио), ~170+ коммитов.
- Никаких хуков нет: нет `.husky/`, нет `commitlint`-конфига, нет `.lefthook*`
  (проверено — файлов нет).
- Формат сообщений сейчас произвольный.

---

## Шаг 1. Посмотреть на текущую историю

```bash
git log --oneline -40
```

Найди проблемные коммиты и запиши их хэши. Нас интересуют конкретно:

- два `feat: test`;
- `feat: updates workflows`;
- три `feat: adds agent loop to real ollama model`.

Реши, что с ними делать:

- **дубли одного изменения** → squash в один коммит с нормальным сообщением;
- **бессмысленное сообщение** (`feat: test`, `feat: updates workflows`) → `reword`
  в осмысленное;
- **несколько несвязанных изменений в одном коммите** → разбить нельзя задним числом
  без боли; если попался такой — оставь как есть, но возьми на заметку на будущее
  (не делай так впредь).

## Шаг 2. Интерактивный rebase

Найди первого «плохого» коммита и перепиши диапазон от его родителя:

```bash
git rebase -i <хэш-родителя-первого-плохого-коммита>
```

В открывшемся редакторе для каждого коммита поставь команду:

- `squash` (или `s`) — склеить с предыдущим (для трёх одинаковых оставить только
  верхний `pick`, двум следующим поставить `s`);
- `reword` (или `r`) — переписать сообщение (для `feat: test`,
  `feat: updates workflows`).

Сформулируй сообщения по конвенции (см. Шаг 3). Например три одинаковых
`feat: adds agent loop to real ollama model` → один
`feat(python-agent): run agent loop against real Ollama model`.

> **Важно про rebase и push.** Rebase переписывает историю: меняются хэши коммитов.
> Если эти коммиты уже запушены, после rebase нужен force-push
> (`git push --force-with-lease`). Это нормально для **своего** портфолио-репо, но
> никогда не делай force-push в общую ветку, с которой кто-то ещё работает. Сначала
> убедись, что никто больше не пушит в этот репозиторий.

## Шаг 3. Принять конвенцию сообщений (Conventional Commits)

Формат:

```
<type>(<scope>): <краткое описание>
```

- **type**: `feat` (новое), `fix` (баг), `refactor`, `docs`, `chore` (тулинг/CI),
  `test`, `perf`, `style`.
- **scope** (опционально): имя приложения/модуля — `go-api`, `python-agent`,
  `react-entrypoint`, `ci`.
- **описание**: что и зачем, в повелительном наклонении, ≤ 72 символа.

Примеры:

- `feat(go-api): add GET /api/applications filtered by env`
- `fix(ci): pin staticcheck via tools.go instead of go install`
- `docs(readme): remove references to deleted react-wrapper`

## Шаг 4. (Опционально, но рекомендую) Автоматическая проверка

Чтобы история не деградировала снова, поставь commitlint + husky:

- `commitlint` проверяет сообщение коммита по правилам conventional commits;
- `husky` вешает хук `commit-msg`, который вызывает commitlint.

Минимальный вариант — без husky: только commitlint-конфиг и запуск вручную/в CI.
Полный вариант — husky + commitlint, чтобы проверка срабатывала автоматически при
каждом коммите. Начни с минимума, добавь husky, если хочется «не думать».

## Критерии готовности

- [ ] В `git log --oneline` больше нет `feat: test` и трёх одинаковых
      `feat: adds agent loop...`.
- [ ] Каждый коммит в последних ~40 — атомарный, с сообщением по конвенции.
- [ ] История по-прежнему собирается/проходит тесты (rebase не сломал код) —
      проверь `git log` после каждого squash/reword и прогни `nx build`/`nx test`
      на финальном состоянии.
- [ ] Если добавил commitlint — новый «плохой» коммит отбивается.

## Подсказки и грабли

- **Не squashatь всё в один гигантский коммит.** Цель — атомарность, а не «один
  коммит на репо». Каждый коммит должен оставлять репо в собираемом состоянии.
- **Делай rebase на чистом дереве.** Сначала `git status` должен быть чистым, иначе
  интерактивный rebase может запутаться.
- **`--force-with-lease` безопаснее `-f`.** Он не перезапишет чужие коммиты, если
  remote ушёл вперёд.
- **Сообщение «что», а не «как».** `feat: test` ничего не сообщает; лучше
  `test(python-agent): add evals for agent tool-calling`.
- **Сохрани бэкап перед rebase**, если боишься:
  `git branch backup-before-rebase` — откатишься в любой момент.
