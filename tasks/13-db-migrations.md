# Задача 13. Миграции БД: goose вместо ручного slice

> Тема: **goose (или golang-migrate)** — заменить ручной список миграций на
> фреймворк с версионированием и накатом.
> Результат: миграции накатываются один раз, с отслеживанием применённых версий,
> в правильном порядке, с возможностью отката.

---

## Зачем

Для solution-роли «миграции руками» — это красный флаг. Сейчас
`apps/go-api/cmd/migrate/main.go` держит **ручной slice** путей к SQL-файлам:

- порядок задан вручную и **не совпадает с нумерацией** файлов: `005` идёт перед
  `002`/`003` (есть комментарий «005 must run before 002/003»);
- **нет таблицы версий** — раннер не помнит, что уже применено. Он просто выполняет
  каждый файл заново при каждом запуске. Это работает только потому, что SQL,
  видимо, идемпотентен (`IF NOT EXISTS` и т.п.), и ломается при первом неидемпотентном
  изменении;
- файл `001` вообще **отсутствует в slice** — базовую схему кто-то накатывает иначе
  (вероятно, сервис `init-db` в docker-compose), а раннер догоняет только «хвост».
  Это два разных механизма наката, которые легко разъезжаются.

Фреймворк решает всё это одной зависимостью: **таблица `goose_db_version`** с
применёнными версиями, **сортировка по версии**, **`up`/`down`**. На собеседовании
«как ты управляешь схемой БД» с ответом «goose с embed-миграциями» — это то, что
хотят услышать.

## Контекст проекта

- `apps/go-api/cmd/migrate/main.go` — текущий ручной раннер (slice + `pgxpool`).
- `apps/go-api/migrations/` — 8 SQL-файлов: `001…008`.
- Go `1.25.0`, модуль `flatty-budget/go-api`, БД через `github.com/jackc/pgx/v5`.
- Зависимостей `goose`/`golang-migrate` сейчас нет.
- Отдельного Nx-таргета `migrate` в `apps/go-api/project.json` нет — миграцию,
  судя по всему, гоняют вручную `go run ./cmd/migrate`.

---

## Шаг 1. Выбрать фреймворк

Рекомендую **goose v3** (`github.com/pressly/goose/v3`):

- это библиотека, а не отдельный бинарь — встраивается в код, миграции можно
  `//go:embed` прямо в бинарь;
- работает поверх `database/sql` и совместима с pgx (`goose` принимает `*sql.DB`,
  а pgx даёт `*pgxpool.Pool` — понадобится адаптер или `stdlib`-драйвер);
- есть `up`/`down`/`status`/`version`, таблица версий по умолчанию `goose_db_version`.

`golang-migrate` — тоже вариант, но чаще тянется как CLI; goose удобнее встраивается.

## Шаг 2. Добавить зависимость и embed

- Добавь `github.com/pressly/goose/v3` в `apps/go-api/go.mod` (через
  `go get` в `apps/go-api`).
- В `cmd/migrate/main.go` замени ручной slice на вызов `goose.Up`.
- Добавь `//go:embed` на директорию миграций, чтобы файлы `migrations/*.sql`
  компилировались в бинарь (тогда `migrate` не зависит от текущей рабочей директории
  и не надо таскать файлы рядом).

## Шаг 3. Разобраться с порядком и отсутствующим 001

Это самое важное и нетривиальное место. Сейчас порядок вручную такой:

```
005 → 002 → 003 → 006 → 007 → 004 → 008   (001 отсутствует)
```

goose накатывает **строго по возрастанию версии** (числовой префикс), то есть
`001 → 002 → 003 → 004 → 005 → 006 → 007 → 008`. Это сломает текущую логику, потому
что `005` (таблица статистики с ключом `(resident_location_id, month, year)`) должна
идти **до** `002`/`003` (backfill-запросы, которые на неё опираются).

Два варианта решения — выбери и обоснуй:

- **(A) Перенумеровать файлы** так, чтобы числовой порядок совпал с реальным порядком
  зависимостей. Например, содержимое `005` становится ранней версией, а `002`/`003`
  сдвигаются. Подходит, если БД можно пересоздать с нуля (в dev так и есть).
- **(B) Сделать миграции независимыми** — переписать `002`/`003` так, чтобы они не
  полагались на `005`, либо объединить связанные шаги в одну версию. Требует правки
  SQL, но сохраняет номера.

Вариант (A) проще и честнее для портфолио, если окружение одноразовое. Что выбрать —
реши сам, но **зафиксируй решение комментарием/документацией**.

Отсутствующий `001`: реши, кто отвечает за базовую схему. Правильный итог — **один
источник правды**: либо `001` входит в goose-набор (и `init-db` его больше не
дублирует), либо явно задокументируй, что `init-db` накатывает только базу, а goose —
всё остальное. Два механизма наката без явного разделения зон — источник рассинхрона.

## Шаг 4. Добавить down-миграции

Для каждой миграции добавь парный `down`-файл (goose именует их
`NNN_xxx.sql` — это `up`, и отдельно down). Если честного отката нет (например,
удаление столбца необратимо) — оставь `down` пустым или с `-- +goose Down` без
операций, но файл должен существовать, чтобы `goose down` не падал.

Минимальный вариант — up-миграции + явное понимание, что откат в dev делается
пересозданием БД. Для портфолио лучше показать хотя бы пару `down`.

## Шаг 5. Добавить Nx-таргет migrate

В `apps/go-api/project.json` добавь таргет `migrate` (по образцу существующих
`build`/`serve`): команда `go run ./cmd/migrate`, `cwd: apps/go-api`. Тогда запуск
станет единообразным: `nx migrate go-api` вместо «помни, что надо `go run ./cmd/migrate`».

Обнови `apps/go-api/AGENTS.md` (таблицу команд) и корневой `README.md`, если там
описан запуск миграций.

## Критерии готовности

- [ ] В `apps/go-api/go.mod` есть goose, в `cmd/migrate/main.go` — вызов `goose.Up`
      с embed, ручной `migrations`-slice удалён.
- [ ] Порядок наката совпадает с реальным порядком зависимостей (005-проблема решена
      перенумерацией или переписыванием SQL).
- [ ] `001` явно включён в набор либо задокументировано его разделение с `init-db`.
- [ ] Повторный запуск миграции на уже применённой БД — no-op (goose это даёт из
      коробки): запусти `nx migrate go-api` дважды, второй раз не должен падать.
- [ ] Есть `migrate` таргет в `project.json`, документация обновлена.

## Подсказки и грабли

- **Не смешивай goose и старый slice.** Переход должен быть «выкинул ручной код,
  оставил только goose», иначе будет два раннера и та же проблема.
- **`//go:embed` и рабочая директория.** Если читаешь файлы с диска (`os.ReadFile`),
  раннер зависит от `cwd`. embed убирает эту зависимость — делай embed.
- **Таблица версий — это состояние.** На уже применённой dev-БД goose-таблицы нет,
  поэтому первый запуск goose попытается накатить всё заново и упадёт на «уже
  существует», если SQL не идемпотентен. Либо пересоздай БД с нуля, либо зафиксируй
  baseline: пометь применённые миграции как выполненные (`goose` умеет baseline).
- **pgx vs database/sql.** goose работает с `*sql.DB`; pgx отдаёт пул. Либо
  используй `pgx` в режиме `stdlib` (`database/sql`-совместимый драйвер), либо
  открывай отдельное `sql.DB` для миграций. Это частый источник путаницы.
- **Down-миграции проверяй.** Напиши `down` — прогони `up` → `down` → `up` на чистой
  БД и убедись, что не падает.
