# Задача 09. Сравнение моделей + отчёт

> Тема: **evals как инструмент выбора модели**. Прогоняем один и тот же golden dataset
> на нескольких моделях Ollama и делаем воспроизводимый отчёт.
> Результат: скрипт + markdown-отчёт «какая модель лучше и почему».

---

## Цель обучения

К концу задачи ты должен уметь:

- переиспользовать eval-harness из задачи 03 для сравнения моделей;
- корректно мерить **качество** и **задержку** (с прогревом и повторами);
- отделять шум от реальной разницы;
- делать вывод «модель X подходит для нашей задачи», подкреплённый цифрами;
- оформлять результат так, чтобы его можно было перепроверить одной командой.

## Контекст

У нас уже есть:
- golden dataset и метрики (задача 03);
- конфигурируемая модель (`OLLAMA_MODEL`).

Теперь нужно прогнать N моделей на одних и тех же кейсах и сравнить. Кандидаты:
`qwen2.5:7b`, `llama3.1:8b`, `mistral` (учитывай, что не все одинаково хорошо умеют
tool-calling — это как раз то, что мы измеряем).

## Шаг 1. Параметризация harness

Сделай так, чтобы модель задавалась снаружи, а не хардкодом. Варианты:

- pytest-параметризация: `@pytest.mark.parametrize("model", MODELS)`;
- или отдельный скрипт `app/scripts/compare_models.py`, который импортирует те же
  `EvalCase` и `run_agent`.

Рекомендую **скрипт** (проще собрать отчёт) + **pytest** для регрессии.

Требования:

- модель передаётся в `run_agent`/`chat`, не читается из глобала;
- кейсы и ожидания — из одного источника (не дублировать golden dataset);
- фиксированные `temperature=0`, `MAX_STEPS`, seed (если поддерживается).

- [ ] Один и тот же код прогоняет любую модель.

## Шаг 2. Что мерить

| Метрика | Как считать | Зачем |
|---|---|---|
| **tool accuracy** | доля кейсов с нужным tool-call | умеет ли модель пользоваться инструментами |
| **numeric accuracy** | доля кейсов с верным числом | правильность ответа |
| **edge-case pass** | кейсы «нет данных»/«не про расходы» | не галлюцинирует ли |
| **latency p50 / p95** | время одного запроса | UX |
| **steps (avg)** | среднее число итераций | эффективность |
| **stability** | совпадение результатов за 3 прогона | надёжность |
| **tool-format errors** | сколько раз ответ не парсится | совместимость |

Требования:

- **прогрев**: первый запрос к модели грузит её в память — не включай в latency
  (сделай 1–2 warm-up вызова и отбрось);
- **повторы**: latency меряй по 3+ прогонам, бери медиану/p95;
- **одинаковые условия**: один golden dataset, один промпт, один MCP-сервер;
- **явно фиксируй версию/квантование модели** (например, `qwen2.5:7b` — это уже тег).

- [ ] Для каждой модели есть accuracy и latency.

## Шаг 3. Запуск

```bash
.venv/bin/python -m app.scripts.compare_models \
  --models qwen2.5:7b llama3.1:8b mistral \
  --runs 3
```

Требования:

- результат сохраняется в машинно-читаемый файл (`reports/model-comparison.json`);
- падение одной модели не роняет весь прогон (ошибка фиксируется как результат);
- прогресс/логи в stderr, итог — в файл.

- [ ] Команда воспроизводима на чистой машине (после `setup`).

## Шаг 4. Отчёт

Сгенерируй `reports/model-comparison.md` примерно такого вида:

```markdown
# Сравнение моделей — 2026-11-10

| Модель | Tool acc | Numeric acc | Edge pass | p50, ms | p95, ms | Avg steps | Stability |
|---|---|---|---|---|---|---|---|
| qwen2.5:7b  | 1.00 | 0.88 | 1.00 | 900  | 1400 | 1.9 | 3/3 |
| llama3.1:8b | 0.88 | 0.75 | 1.00 | 1200 | 2000 | 2.3 | 2/3 |
| mistral     | 0.63 | 0.50 | 0.75 | 700  | 1100 | 1.2 | 1/3 |
```

Плюс раздел «Вывод»:

- какая модель рекомендуется и **почему**;
- какие кейсы провалила каждая (id кейсов);
- ограничения замера (локальные модели, квантование, железо, сеть).

Требования:

- отчёт генерируется скриптом, а не пишется руками;
- в отчёте есть дата, список моделей, версия промпта/кейсов;
- вывод опирается на цифры, а не на «мне показалось».

- [ ] Отчёт читается человеком и перепроверяется командой.

## Шаг 5. Интерпретация (важная часть)

Ответь себе письменно:

- Где модели **расходятся**? (выбор инструмента? числа? формат?)
- Есть ли кейсы, которые валит **все**? Значит, проблема в промпте/инструменте, а не в
  модели.
- Стоит ли маленькая разница в accuracy разницы в latency?
- Что важнее для продукта: точность или скорость?

Это и есть навык «evals → решение», а не просто «прогнал тесты».

- [ ] В отчёте есть раздел с интерпретацией и рекомендацией.

## Подсказки и грабли

- **Холодный старт.** Первый вызов грузит модель — иначе получишь «медленную» модель,
  которая на самом деле просто не была в памяти. Прогревай.
- **Разные форматы tool-calls.** Одна модель вернёт `tool_calls`, другая — текст с
  JSON. Считай это отдельной метрикой (`tool-format errors`), а не «багом».
- **Малая выборка.** 8 кейсов — это мало для статистики. Не делай громких выводов из
  разницы в 1 кейс; смотри на паттерны.
- **Одинаковый контекст.** Меняй **только** модель. Промпт, инструменты, данные — те же.
- **Квантование.** `qwen2.5:7b` может быть разным на разных хостах. Зафиксируй, где
  запускал.
- **Сеть.** Ollama удалённый (`192.168.1.85`) — latency включает сеть. Отметь это или
  меряй отдельно время генерации из ответа (если отдаёт `eval_duration`).
