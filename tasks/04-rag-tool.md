# Задача 04. RAG как инструмент: семантический поиск по расходам

> Тема: **классический RAG** (эмбеддинги + поиск по смыслу) — но встроенный правильно:
> как один из инструментов агента, а не как замена SQL.
> Результат: новый MCP-инструмент `search_expenses(query)`, который находит траты по
> смыслу `description`.

---

## Цель обучения

К концу задачи ты должен уметь:

- объяснить, **когда RAG, а когда tool-calling/SQL**, и не путать эти инструменты;
- получать эмбеддинги через Ollama (`nomic-embed-text`);
- хранить векторы в Postgres и считать косинусное сходство;
- строить идемпотентный индекс (переиндексация без дублей);
- отдавать поиск как MCP-инструмент и подключать его к агенту из задачи 02.

## Зачем RAG, если уже есть tool-calling

Задача 02 отвечает на **числовые** вопросы («сколько потрачено в январе»). Но есть
вопросы другого типа:

- «Найди траты, где описание про интернет или связь».
- «Что мы покупали для ремонта?»
- «Есть ли что-то про парковку?»

Здесь нужен поиск **по смыслу текста**, а не `SUM`. Классический RAG (векторный поиск)
для этого и предназначен. Важно: это **дополнительный инструмент**, а не замена
`get_monthly_totals`. Агент сам выберет, что вызвать.

> Правило: **числа — SQL, смысл — эмбеддинги.** Не пытайся считать суммы через RAG.

## Шаг 1. Эмбеддинги (`app/rag/embeddings.py`)

Ollama Python умеет эмбеддинги:

```python
from ollama import AsyncClient

client = AsyncClient(host="http://192.168.1.85:11434")
resp = await client.embed(model="nomic-embed-text", input=["текст 1", "текст 2"])
vectors = resp.embeddings          # list[list[float]], размерность 768
```

Требования:

- `embed_texts(texts: list[str]) -> list[list[float]]` — батчами (Ollama принимает
  список), с таймаутом и понятной ошибкой;
- модель эмбеддингов — из конфига (`OLLAMA_EMBED_MODEL`), не хардкод;
- **нормализуй** векторы (L2), тогда косинус = скалярное произведение — проще и быстрее;
- пустой/слишком длинный текст обрабатывай явно (обрезка до лимита модели).

- [ ] Эмбеддинг одной строки возвращает вектор длины 768 (проверь фактическую).

## Шаг 2. Хранилище векторов

Два варианта — выбери один.

**A. Без расширений (рекомендую для старта).** Таблица:

```sql
CREATE TABLE IF NOT EXISTS expense_embeddings (
    expense_id  BIGINT PRIMARY KEY REFERENCES expenses(id) ON DELETE CASCADE,
    embedding   DOUBLE PRECISION[] NOT NULL,
    model       TEXT NOT NULL,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Поиск: достать векторы (с фильтрами по `resident_location_id`/`year` через JOIN) и
посчитать косинус в Python/numpy. Для десятков тысяч строк это нормально.

**B. pgvector.** Нужен образ `pgvector/pgvector:pg16` (в проекте сейчас `postgres:16`,
без расширения). Тогда:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
ALTER TABLE expense_embeddings ADD COLUMN vec vector(768);
-- поиск: ORDER BY vec <=> $1 LIMIT k
```

Плюс: индекс `ivfflat`/`hnsw` и поиск на стороне БД. Минус: надо менять инфраструктуру.

## Шаг 3. Индексер (`app/rag/indexer.py`)

Скрипт/функция, которая:

1. выбирает `expenses` **без** актуального эмбеддинга (LEFT JOIN / `updated_at`);
2. строит текст для эмбеддинга (например, `category_name + ": " + description`);
3. батчами получает векторы;
4. делает upsert (`ON CONFLICT (expense_id) DO UPDATE`);
5. логирует сколько обработано/пропущено.

CLI:

```bash
.venv/bin/python -m app.scripts.index_embeddings
```

Требования:

- **идемпотентность**: повторный запуск не создаёт дублей и не пересчитывает всё зря;
- пересчёт при изменении `description` (сравнивай `updated_at`);
- не падать на пустых описаниях (пропускать или использовать категорию).

- [ ] Первый запуск индексирует все траты.
- [ ] Второй запуск — «0 новых», быстро.

## Шаг 4. Поиск (`app/rag/search.py`)

```python
async def search_expenses(
    query: str,
    resident_location_id: int,
    limit: int = 5,
) -> list[dict[str, object]]:
    """Найти траты по смыслу описания."""
```

Требования:

- эмбеддинг запроса → косинус с кандидатами → top-k;
- фильтры по `resident_location_id` (и опционально `year`);
- в ответе — `expense_id`, `description`, `amount`, `month`, `year`, `score`;
- `score` в [0..1], округлённый (не отдавай «сырые» -0.0001);
- ограничение `limit` (например, ≤ 20), чтобы не выгрузить всю таблицу.

- [ ] Запрос «интернет» находит траты с `internet_tv` / описанием про интернет.
- [ ] Запрос «ремонт» находит релевантные, если такие есть; иначе пустой список.

## Подсказки и грабли

- **Размерность.** У `nomic-embed-text` — 768. Если меняешь модель, меняется и
  размерность: храни `model` рядом с вектором и переиндексируй при смене.
- **Нормализация.** Без L2-нормализации косинус считать дольше; нормализуй один раз при
  записи (и запрос тоже).
- **Свежесть индекса.** Новые траты появляются через go-api. Индекс не обновится сам —
  нужен cron/скрипт или хук. Это честное ограничение, отметь его.
- **Кэш эмбеддингов.** Одинаковые описания не пересчитывай (хэш текста → вектор).
- **`DOUBLE PRECISION[]` и psycopg3.** Передавай список как `list[float]`; для
  `real[]`/`vector` — проверь адаптацию.
- **Не смешивай с суммами.** RAG не умеет складывать. Это работа SQL.
