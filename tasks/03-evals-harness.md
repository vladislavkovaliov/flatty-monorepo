# Задача 03. Evals: как проверять агента

> Тема: **оценка (evals) LLM-агентов** на детерминированных данных.
> Результат: pytest-harness, который сидит БД известными данными, задаёт агенту
> вопросы и сверяет точные числа и выбранные инструменты.

---

## Цель обучения

К концу задачи ты должен уметь:

- объяснить, почему «посмотрел глазами и вроде ок» — не eval;
- строить **golden dataset**: вопрос → ожидаемый ответ → ожидаемые инструменты;
- делать **детерминированный сидинг** БД, не зависящий от реальных данных;
- разделять оценку на слои: «детерминированное ядро» (инструменты/репозитории) и
  «вероятностная оболочка» (LLM);
- считать метрики и читать отчёт: pass rate, tool accuracy, numeric accuracy;
- снижать флаки (температура, лимиты, изоляция).

## Идея: оценивай слои по отдельности

Агент — это LLM + инструменты. Ошибка может быть в любом месте. Поэтому evals делят на:

| Слой | Что проверяем | Детерминизм |
|---|---|---|
| **Репозитории / инструменты** | SQL и агрегаты дают верные числа | полный |
| **Выбор инструмента** | на вопрос агент зовёт правильный tool | почти полный |
| **Финальный ответ** | число в ответе совпадает с эталоном | вероятностный |

Если падает слой инструментов — чинить SQL, а не промпт. Это ускоряет отладку в разы.

## Шаг 0. Изоляция тестовой БД

Нельзя сидить данные в `flatty` рядом с реальными. Варианты (выбери один):

1. **Отдельная БД** `flatty_eval` в том же Postgres (рекомендую):
   создаётся один раз, схема — из `db.sql` + миграций go-api.
2. **Отдельная схема** (`CREATE SCHEMA eval`) и `search_path`.
3. **Транзакция на тест** с `ROLLBACK` в конце — если всё укладывается в одну транзакцию.

Задай в `.env.eval`:

```
DATABASE_URL=postgres://postgres:password@localhost:55000/flatty_eval?sslmode=disable
```

Сидинг удобно делать через `psql`/`db.sql` один раз, а тестовые данные вставлять
фикстурами. **Никогда не полагайся на продовые данные** — иначе eval невоспроизводим.

- [ ] `flatty_eval` (или схема) существует, схема таблиц на месте.
- [ ] Тесты не трогают `flatty`.

## Шаг 1. Golden dataset

Создай `tests/golden.py` (или `tests/golden.json`) — список кейсов. Формат предложи сам,
но в каждом кейсе должно быть:

```python
@dataclass(frozen=True)
class EvalCase:
    id: str
    question: str
    expect_tools: set[str]      # какие инструменты обязан вызвать
    expect_value: float | None  # ожидаемое число (если применимо)
    tolerance: float = 0.01
```

Покрой **все** типы:

- агрегат-сумма → `get_monthly_totals`;
- среднее → `get_monthly_averages`;
- список трат → `list_expenses`;
- справочник → `list_categories`;
- доступные месяцы → `get_years_months`;
- **edge cases**: месяц без данных (0 / пусто), несуществующий `resident_location_id`,
  вопрос вообще не про расходы (не должно быть tool-вызовов).

- [ ] В golden dataset ≥ 8 кейсов, включая 2 edge case.

## Шаг 2. Детерминированный сидинг

`tests/conftest.py`:

- фикстура, которая **очищает** тестовые таблицы и вставляет известный набор:
  например, `resident_location_id = 999`, `year = 2099`, категории с предсказуемыми
  суммами;
- срок жизни: на функцию/модуль — как удобнее, но состояние должно быть одинаковым
  в каждом прогоне;
- после теста — очистка (или rollback).

Пример ожидаемых данных (придумай свои, но зафиксируй):

| Категория | Январь 2099 | Февраль 2099 |
|---|---|---|
| utilities | 100.00 | 50.00 |
| electricity | 30.00 | 20.00 |
| **итого `total_spent`** | **130.00** | **70.00** |

Тогда ответ на «сколько в январе 2099» = `130.00`, на «среднее в январе» = `65.00`
(при `expense_count=2`).

- [ ] Прогон сидинга дважды подряд даёт одинаковое состояние.
- [ ] Известные суммы посчитаны заранее вручную и зафиксированы в кейсах.

## Шаг 3. Оценка ядра (без LLM)

Быстрые и стабильные тесты на репозитории/инструменты:

- `get_monthly_totals(999, 2099, 1)` → `[{"total_spent": 130.0, ...}]`;
- `get_monthly_averages(...)` → среднее и `expense_count`;
- `list_expenses(...)` → ровно N записей, фильтры работают;
- `list_categories()` → все категории.

Это ловит ошибки SQL и конвертации `Decimal → float` до того, как в дело вступит LLM.

- [ ] `pytest tests/test_repositories.py` — зелёный, ~миллисекунды.

## Шаг 4. Eval выбора инструментов и ответа

Два способа прогнать агента; выбери по вкусу:

**A. In-process** — импортировать `run_agent` и вызвать напрямую с тестовой конфигурацией.
Быстрее, не нужен поднятый HTTP.

**B. Через HTTP** — поднять приложение (`httpx.ASGITransport`) и дергать `POST /chat`.
Ближе к реальности.

Рекомендую **A** для скорости + один smoke-тест через **B**.

```python
async def test_months_total(eval_case: EvalCase, agent_session) -> None:
    result = await run_agent(agent_session, eval_case.question)
    assert eval_case.expect_tools <= set(result.used_tools)
    if eval_case.expect_value is not None:
        assert extract_number(result.answer) == pytest.approx(eval_case.expect_value, abs=0.01)
```

Требования:

- `temperature=0`, `MAX_STEPS` фиксирован;
- извлечение числа из ответа — отдельная функция `extract_number` (парсинг чисел,
  поддержка запятой/точки, пробелов-разделителей). Покрой её юнит-тестами;
- для «светской беседы» — `expect_tools == set()`.

- [ ] Каждый кейс либо проходит, либо падает с понятным сообщением (видны вопрос,
      ожидание, факт).

## Шаг 5. Метрики и отчёт

Собери сводку по прогону:

- **tool accuracy** — доля кейсов, где нужный инструмент вызван;
- **numeric accuracy** — доля кейсов с верным числом;
- **no-hallucination** — на edge case агент не выдумал цифру.

Например, фикстура `session`-scope собирает результаты и печатает таблицу в конце.
Не обязательно делать красиво — достаточно читаемого вывода. Но важно: **падение
метрики должно валить CI**.

- [ ] `nx test python-expense-agent` печатает сводку и возвращает ненулевой код при
      провале.

## Шаг 6. Стабильность (анти-флаки)

Прогони eval 3 раза подряд. Если результаты «прыгают»:

- понизь температуру (или `temperature=0`, `seed` если поддерживается);
- упрости вопрос/промпт;
- убери зависимость от порядка инструментов;
- для числовых сверок используй допуск, для выбора инструментов — множество, не порядок;
- не сравнивай дословный текст ответа — только число и факт вызова.

- [ ] 3 прогона из 3 дают одинаковый результат.

## Критерии готовности

- [ ] `nx test python-expense-agent` — зелёный на чистой `flatty_eval`.
- [ ] Есть ≥ 8 кейсов, покрыты агрегаты, список, справочник, edge cases.
- [ ] Есть отдельные быстрые тесты репозиториев (без LLM).
- [ ] Есть отчёт с tool accuracy и numeric accuracy.
- [ ] При искусственной поломке (например, вернуть неверную сумму) тест **краснеет**.
      Проверь это руками — это доказывает, что eval реально что-то ловит.
- [ ] Тесты не зависят от реальной БД `flatty` и от сети, кроме Ollama.

## Подсказки и грабли

- **Не eval-ь на реальных данных.** Любое изменение в `flatty` сломает ожидания.
- **LLM недетерминирован.** Не утверждай `answer == "..."`. Утверждай число/факты.
- **Числа в тексте.** «130 рублей», «130,00», «130.0» — нормализуй перед сравнением.
- **Замаскированный провал.** Если тест всегда зелёный, попробуй испортить код — он
  должен упасть. Иначе ты проверяешь не то.
- **Скорость.** Слой репозиториев держи быстрым; LLM-тестов немного.
- **Изоляция.** Параллельный pytest + общая БД = гонки. Либо последовательно, либо
  своя схема на воркер.
