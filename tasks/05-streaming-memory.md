# Задача 05. Streaming и память диалога

> Тема: **потоковая выдача (SSE)** + **многоходовой диалог** для агента.
> Результат: `/chat` умеет стримить токены, а агент помнит контекст в рамках сессии.

---

## Цель обучения

К концу задачи ты должен уметь:

- стримить ответ LLM через FastAPI (`text/event-stream`);
- правильно совмещать стриминг с **tool-calling** (tool-calls приходят частями);
- хранить историю диалога и передавать её в модель;
- управлять бюджетом контекста (обрезка/суммаризация);
- не сломать уже работающие evals из задачи 03.

## Зачем это нужно

Обычный `/chat` из задачи 02 ждёт весь ответ целиком. Для UX это плохо: 3–10 секунд
тишины. Streaming отдаёт токены по мере генерации. Плюс без истории нельзя спросить
«а в феврале?» — модель не знает, о чём был предыдущий вопрос.

## Часть A. Streaming

### Шаг 1. Стриминг Ollama

```python
stream = await client.chat(
    model=MODEL,
    messages=messages,
    tools=tools,
    stream=True,
)
async for chunk in stream:
    if chunk.message.content:
        yield chunk.message.content
    if chunk.message.tool_calls:
        ...   # приходит частями!
```

Особенность: при `stream=True` `tool_calls` могут приходить **по кускам**
(имя/аргументы). Их нужно накапливать, а не обрабатывать каждый чанк как отдельный
вызов. Аргументы — это JSON-строка, которую надо склеить и распарсить в конце.

Требования:

- собрать все дельты tool-call в один вызов до исполнения;
- после исполнения инструмента — продолжить стриминг следующего шага;
- лимит итераций (`MAX_STEPS`) сохраняется.

- [ ] Ответ стримится, tool-calls при этом не ломаются.

### Шаг 2. SSE-endpoint

Добавь `POST /chat/stream`, возвращающий `text/event-stream`:

```python
from fastapi.responses import StreamingResponse

@app.post("/chat/stream")
async def chat_stream(req: ChatRequest) -> StreamingResponse:
    async def events():
        async for event in run_agent_stream(...):
            yield f"data: {json.dumps(event, ensure_ascii=False)}\n\n"
    return StreamingResponse(events(), media_type="text/event-stream")
```

Формат событий предложи сам, но он должен различать:

- `token` — кусок текста;
- `tool_call` — какой инструмент вызван (для отладки/UI);
- `done` — финал (можно с `used_tools`);
- `error` — ошибка.

Требования:

- SSE-кадр: `data: <json>\n\n` (двойной перевод строки — разделитель);
- заголовки против буферизации: `Cache-Control: no-cache`, `X-Accel-Buffering: no`;
- корректно обрабатывать обрыв соединения клиентом (не течь);
- `used_tools` всё ещё доступен (в `done`).

- [ ] `curl -N` показывает токены по мере поступления.
- [ ] Финальное событие `done` содержит `used_tools`.

### Шаг 3. Проверка

```bash
curl -N localhost:8100/chat/stream -H 'content-type: application/json' \
  -d '{"message":"Сколько потрачено в январе 2023?","resident_location_id":1}'
```

- [ ] Видно инкрементальную выдачу.
- [ ] Стриминговый и обычный endpoint дают одинаковый итоговый ответ.

## Часть B. Память диалога

### Шаг 4. Модель сессии

Выбери вариант:

**A. Клиентская история (проще).** `POST /chat` принимает `history: list[Message]`,
клиент сам хранит её. Сервер stateless. Хорошо для API и evals.

**B. Серверная сессия.** `session_id` + хранилище (in-memory dict или Redis). Удобнее
для UI/Telegram, но нужен TTL и очистка.

Рекомендую начать с **A**, затем при желании добавить **B**.

```python
class ChatRequest(BaseModel):
    message: str
    resident_location_id: int = 1
    session_id: str | None = None
    history: list[Message] = []
```

Требования:

- храни **только** `user`/`assistant` реплики (не тащить сырые tool-сообщения в
  историю клиента — они раздувают контекст);
- валидируй роли и размер истории;
- `session_id` (если B) — TTL, лимит сессий, изоляция.

- [ ] «Сколько в январе?» → «А в феврале?» отвечает про февраль, а не переспрашивает.

### Шаг 5. Бюджет контекста

История растёт и однажды переполнит окно модели. Сделай хотя бы одно:

- **обрезка**: оставлять последние N реплик (и/или M токенов, грубая оценка);
- **суммаризация**: старые реплики сжать в одно `system`-сообщение;
- **окно по времени**: хранить последние T минут.

Требования:

- системный промпт не выкидывается никогда;
- при обрезке не разрывай пару tool-call/tool-result (иначе модель запутается);
- поведение задокументируй.

- [ ] При длинном диалоге запрос не падает по context length.
- [ ] Старые детали теряются предсказуемо (не «случайно»).

## Подсказки и грабли

- **Буферизация.** Nginx/прокси могут копить поток. `X-Accel-Buffering: no` и
  `Cache-Control: no-cache` обязательны.
- **Сборка tool-call.** Не парси аргументы на каждом чанке — копи дельты, парси в конце.
- **`async for` и отмена.** Клиент ушёл — отмени генерацию, иначе впустую жжёшь модель.
- **История и evals.** Если добавил `history` в запрос — сделай поле необязательным,
  чтобы старые кейсы не менялись.
- **Дублирование.** Стриминговый и нестриминговый пути должны использовать **один**
  агентный цикл, иначе разъедутся.
- **SSE ≠ WebSocket.** Для одного потока событий SSE проще; WebSocket нужен для
  двустороннего обмена.
